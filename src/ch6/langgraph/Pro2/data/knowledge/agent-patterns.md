# Agent 设计模式

## ReAct 模式
ReAct (Reason + Act) 是最常用的 Agent 模式。Agent 在每一步都先推理（Reason），然后行动（Act），观察结果后再决定下一步。

补充说明：

- 推理阶段：LLM 分析当前状态、思考可用工具和预期结果，生成一个“思考”文本。
- 行动阶段：调用选定的工具（如搜索引擎、API、数据库）并获取返回结果。
- 观察阶段：将工具输出作为新的上下文，输入给下一轮推理，形成闭环。

适用场景：问题分解明确、步骤可串行的任务，如信息检索、客服问答、简单数据分析。

优缺点：实现简单，可解释性强；但容易陷入冗长的推理链，对长上下文消耗大，且缺乏全局规划能力。

# 其他常见 Agent 模式
## Plan-and-Execute 模式
核心思想：先由 LLM 生成一份完整的执行计划（步骤列表），再按计划逐步执行，每步执行后可根据中间结果微调后续计划。

优势：全局视野更好，避免 ReAct 的“走一步看一步”导致的偏离；适合复杂多步骤任务（如旅行规划、项目生成）。

挑战：计划生成依赖 LLM 的规划能力，若初始计划错误则后续执行易失败；需设计计划验证机制。

## Reflection（反思）模式
核心思想：Agent 在执行完一个阶段后，启动一个“反思”过程（通常用另一个 LLM 或同一 LLM 的不同 prompt），对自身输出进行批判性评价，指出不足并给出改进建议，然后重新生成结果。

典型应用：代码生成、写作润色、数学解题等需要迭代优化的场景。

实现方式：可使用多轮对话，或在 LangGraph 中构建“生成 → 反思 → 修改”的循环节点。

## LLM Compiler / 并行执行模式
核心思想：将任务分解为可并行执行的子任务，多个 Agent 或工具同时运行，最后汇总结果。适用于需要多源数据聚合的场景（如同时查询多个数据库、比对多个模型输出）。

# 多 Agent 模式（扩展）
## Supervisor 模式（监督者模式）
中心调度器（Supervisor）负责接收任务、分解子任务、分发给不同的 Worker Agent，并汇总最终结果。

Supervisor 本身不执行具体任务，只做路由和决策。

适合任务类型多样、需要不同专家 Agent 协作的系统（如财务分析 + 市场调研 + 风险评估）。

## Swarm 模式（群体/交接模式）
Agent 之间直接交接（handoff），没有中心控制器。每个 Agent 知道自己能处理什么，不能处理什么，当遇到无法处理的任务时，将控制权转交给另一个 Agent。

适合流程动态变化、Agent 能力边界清晰的场景（如客服工单流转）。

注意防止循环交接，需设置最大交接次数。

## Hierarchical 模式（层级模式）
构建多级管理层：高层 Agent 制定战略目标，中层分解为战术任务，底层执行具体操作。

适用于大型组织模拟、供应链管理、军事推演等需要分层决策的系统。

复杂度高，需设计好上下级通信协议和抽象粒度。

## 协作模式（Collaborative / Debate 模式）
多个 Agent 围绕同一问题提出观点，通过讨论或辩论达成一致（或由裁判 Agent 裁决）。

可提升事实准确性，减少单一模型的偏见。常用于事实核查、复杂推理任务。

工具设计原则
明确输入输出 Schema：使用 JSON Schema 或 Pydantic 模型定义工具参数，让 LLM 精确理解。

提供示例：在工具描述中加入少量使用示例（few-shot），帮助 LLM 在上下文中正确调用。

错误友好：工具应返回结构化的错误信息（如 {"error": "timeout", "retry": true}），便于 Agent 判断重试或更换策略。

幂等性：尽量设计幂等操作，防止重复调用导致副作用（如重复扣款）。

# 记忆管理
Agent 需要维护短期记忆（当前对话上下文）和长期记忆（向量数据库存储历史案例、用户偏好）。

- 短期记忆：使用滑动窗口或摘要策略，控制上下文长度。

- 长期记忆：通过 RAG（检索增强生成）在需要时检索相关历史信息，注入到 prompt 中。

- 记忆清除策略：在每次任务结束时清理无用记忆，避免干扰后续任务。

最佳实践（扩展）
   - 工具描述要清晰，包含工具名称、功能、参数列表、返回值格式，帮助 LLM 正确选择。

   - 设置最大迭代次数（如 10 轮）和超时时间，防止无限循环或长时间空转。

   - 每个步骤的输入输出要可追踪，使用唯一 ID 记录日志，便于调试和审计。

使用 LangGraph 管理复杂工作流，通过状态图和条件边精确控制 Agent 流程，支持循环、并行、分支。

结构化输出：要求 Agent 输出 JSON 或特定格式，方便后续解析和程序化处理。

异常处理：对工具调用失败、LLM 解析错误、计划执行超时等情况，设计回退策略（如重试、降级、人工介入）。

评估与监控：离线评估 Agent 的任务成功率、工具调用准确率、平均步数；线上监控 token 消耗、延迟、错误率。

提示词工程：为不同角色（推理者、执行者、反思者）设计专门的 system prompt，明确职责边界。

结果验证：对于关键任务（如订单支付），增加独立验证 Agent 或规则校验，确保最终输出符合预期。

版本控制：对工具、prompt、模型版本做记录，便于回滚和 A/B 测试。

常见陷阱与应对
陷阱	应对方案
Agent 过度依赖某个工具，导致误用	在工具描述中加入“适用条件”和“不适用场景”
推理链过长，消耗大量 token	使用 Plan-and-Execute 先规划，或限制每步推理长度
多 Agent 间沟通信息丢失	使用全局状态（如 LangGraph 的 State）共享上下文
Agent 产生幻觉，捏造结果	增加事实核查工具，或引入 Reflection 模式自检
工具调用顺序混乱	用状态机或工作流引擎（如 LangGraph）强制顺序
架构演进趋势
从单 Agent 到多 Agent 协作：复杂任务分解成为主流。

从固定模式到动态自适应：Agent 可根据任务难度动态选择策略（如简单问题用 ReAct，复杂问题用 Plan-and-Execute）。

融合强化学习：通过 RL 优化 Agent 的决策策略，而非仅靠 LLM 的 prompt。

人机协同：在关键节点引入人工审批或修正，提高可靠性。
