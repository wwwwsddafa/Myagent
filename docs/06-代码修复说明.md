## 1. F1 · `src/ch4/reflection.py` 补全（最严重）

### 1.1 修复前现象
```
>>> import reflection
Traceback (most recent call last):
  ...
  File "src/ch4/reflection.py", line 2, in <module>
    from llm import HelloAgentsLLM
ImportError: cannot import name 'HelloAgentsLLM' from 'llm'
```
导入即失败，原因是：
1. **类名拼写错误**：代码写 `HelloAgentsLLM`（多了一个 s），而 `llm.py` 中真实类名是 `HelloAgentLLM`。
2. **`Memory` 类完全缺失**：第 3 行 `from memory import Memory` 指向一个不存在的模块/类。
3. **三个方法体是 `...` 占位符**：`ReflectionAgent.__init__`、`_get_llm_response`、以及一处解析逻辑都是 `pass`/`...`，无法运行。
4. **Prompt 模板内容为空**：`INITIAL_PROMPT_TEMPLATE`、`REFINE_PROMPT_TEMPLATE` 为空字符串；而 `REFLECT_PROMPT_TEMPLATE` 直接**误用了 ReAct 模板**（写了 `Thought/Action/Observation`，但 Reflection 范式根本不需要工具调用），逻辑错位。

### 1.2 根因
这是一处**只写了框架、没写完实现**的半成品——简历上写了「Reflection 范式」，但代码跑不起来。面试若被追问「讲讲你的 Reflection 实现」会当场露怯。

### 1.3 修复方案
完整重建 `reflection.py`，严格对齐 ReAct / Plan-and-Solve 同目录代码风格：

- **`Memory` 类**（从零实现）：
  - 内部用列表 `self.records` 保存 `(record_type, content)` 轨迹；
  - `add_record(type, content)`：校验 `type ∈ {execution, reflection}`，非法值抛 `ValueError`；
  - `get_last_execution()`：倒序找到最后一条 `execution`；
  - `get_execution_count()` / `get_trajectory()`：供调试与日志。
- **`ReflectionAgent` 类**：
  - `__init__(llm_client, max_iterations=3)`：持有 LLM 客户端、迭代上限、独立 `Memory` 实例；
  - `_get_llm_response(prompt)`：调用 `llm_client.think([...])` 拿到模型文本；
  - `_extract_code(text)`：用正则剥离 ```python 代码围栏，清洗出可执行代码（与 react_agent 的清洗逻辑一致）；
  - `_parse_reflection(text)`：从「反思」文本中抽取 `needs_refinement`(bool) 与 `refinement_suggestion`(str)；
  - `run(task)`：主循环 = 执行 → 评测 → 反思 →（如需）精炼 → 再执行，直到通过或达 `max_iterations`。
- **三套 Prompt 模板**（全部补齐真实内容）：
  - `INITIAL_PROMPT_TEMPLATE`：首轮「直接写代码」指令；
  - `REFLECT_PROMPT_TEMPLATE`：**重写为 Reflection 专属的「代码评审 + 改进建议」模板**（不再混入 ReAct 的 Action/Observation）；
  - `REFINE_PROMPT_TEMPLATE`：基于反思建议「重写改进版代码」指令。

## 2. F2 / F3 / F4 · 环境变量加载路径（跨目录崩溃）

### 2.1 修复前现象
从仓库根目录（或任意非项目子目录）运行 AutoGen / Pro1 时：
```
Traceback (most recent call last):
  ...
  raise ValueError("未找到 API Key，请设置 LLM_API_KEY ...")
```
`.env` 实际位于**仓库根** `data/.env`，但三个项目的 `_load_env()` 只向上查找了 **2 层**，而文件嵌套在 `src/ch6/autoGen-demo/`（3 层深），因此永远够不到 `data/.env`，只能 fallback 到系统环境变量 → 读不到 Key → 抛异常。

### 2.2 根因
路径搜索是「写死的候选列表，最多上溯 2 级」，不具泛化性。文件层级稍深就失败。

### 2.3 修复方案（统一）
将 `_load_env()` 改为**从 `__file__` 所在目录开始，逐层向上遍历，直到找到 `data/.env` 或 `.env` 为止**：
```python
def _load_env():
    current_file = os.path.abspath(__file__)
    dir_to_check = os.path.dirname(current_file)
    while True:
        for path in (os.path.join(dir_to_check, "data", ".env"),
                     os.path.join(dir_to_check, ".env")):
            if os.path.exists(path):
                load_dotenv(path, override=True)
                print(f"✅ 已加载环境变量: {path}")
                return True
        parent = os.path.dirname(dir_to_check)
        if parent == dir_to_check:   # 到达文件系统根
            break
        dir_to_check = parent
    load_dotenv()                    # 兜底：基于 cwd
    return False
```
- AutoGen 项目最终会命中仓库根的 `data/.env`（Key 命名 `OPENAI_*` 与代码里的 `LLM_* or OPENAI_*` 回退逻辑兼容）；
- Pro2 的 `.env` 在 `src/ch6/langgraph/Pro2/.env`，由独立的 `_env.py` 处理（见 F5）。
- F4 的 Pro1 是**模块级**就建客户端（`llm = ChatOpenAI(...)`），修复前找不到 .env 会直接抛异常让整个模块无法导入；修复后导入即成功。

### 2.4 验证（已通过，无网络请求）
从**仓库根目录**进入各项目子目录运行：
```

✅ 已加载环境变量: C:\Users\wc\Desktop\agents\data\.env   # autoGen-test
✅ 已加载环境变量: C:\Users\wc\Desktop\agents\data\.env   # Pro1

### 3.2 修复方案

```python
import os
from dotenv import load_dotenv

def load_project_env() -> None:
    cur = os.path.dirname(os.path.abspath(__file__))
    while True:
        env_path = os.path.join(cur, ".env")
        if os.path.exists(env_path):
            load_dotenv(env_path, override=True)
            return
        parent = os.path.dirname(cur)
        if parent == cur:
            break
        cur = parent
    load_dotenv()   # 兜底

load_project_env()
```
5 个模块把 `from dotenv import load_dotenv` / `load_dotenv()` 替换为 `from _env import load_project_env` / `load_project_env()`。
> 注：`tools/knowledge.py` 原本就用 `os.path.dirname(os.path.dirname(abspath(__file__)))` 正确定位 `Pro2/.env`，无需改动。
